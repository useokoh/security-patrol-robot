- 알려진 영향: 같은 값이 '막 생긴 사건이 움직이면 근처 정지 사건과 합치기' 시간에도 쓰여, 3 m 방에서는 합치기가 더 잦아진다.

## 2026-11-03 실제 순찰·감지·휴대폰 알림 성공 (8-4, 8-5)
- 확인 결과:
  - 방 가운데를 원점으로 지도를 다시 만들고(사용자 선택 B), 벽에서 떨어진 4지점 네모 경로(`~/maps_real/patrol_route_safe.yaml`, 1.4 × 0.65 m)로 순찰. 1바퀴 164초, 4/4 도착, 복구 동작 0번. 지점 사이 31~47초.
  - 사람 없이 약 5분 순찰하는 동안 감지 0건(오경보 0).
  - 사람이 들어가 서 있다가 걷자 휴대폰 알림이 왔다(18:09~18:10): 주의 새 사건 → 사람 후보 추가 → 긴급 등급 상승. 오늘 추가한 '사람 후보 추가' 알림과 B안 합치기('같은 대상: 사건 #3')가 실제로 동작했다.
- 문제: 한 사람이 약 1분 걸은 동안 사건이 #1~#4 로 나뉘고 알림이 9개 이상 왔다. 순찰 중 회전할 때 감지를 쉬고, 실제 방에서 다리가 따로 잡히거나 놓친 뒤 10초(relink_sec)·0.5 m(same_place_dist)를 넘겨 다시 잡힌 것으로 본다. 감지 터미널 기록으로 원인을 확인하지는 않았다.
- 문제와 해결: 순찰 프로그램이 `/amcl_pose` 를 한 번도 못 받아 기다림. 원인은 `real_nav` 를 끈 탭에서 순찰을 실행해 Nav2 가 꺼져 있었던 것(`/initialpose` 구독자 0). 남은 프로세스를 정리하고 다시 켜서 해결.

## 2026-11-03 실제 로봇 연결·지도·순찰 첫 시도
- 확인 결과:
  - 8-1 연결 성공: 로봇 → 맥 중계 → VM agent 로 초당 약 113개 패킷(바퀴 100 Hz + 라이다 조각). RViz 에 실제 라이다 점.
  - 8-3 실제 방(약 3.3 × 3.4 m) 지도 저장, 벽이 한 겹으로 깨끗함. odom 과 SLAM 정상.
  - 8-4 순찰: 위치추정은 맞았지만 구석 출발과 도착 방향 맞추기에서 복구 동작이 반복됨.
- 문제와 해결:
  - 중계가 멈춤: agent 가 꺼진 동안 send 가 '연결 거부' 오류를 먼저 가져가고, select 가 읽을 수 있다고 한 소켓의 recv 가 영원히 기다렸다. 소켓을 non-blocking 으로 바꾸고 재현 시험을 추가했다.
  - 로봇이 확인 신호만 보내고 데이터가 없음: 펌웨어는 agent 없이 부팅하면 ROS 연결을 만들지 못한 채 ping 만 성공해 재부팅하지 않는다. 규칙: VM launch 를 먼저 켜고 로봇을 켜거나 리셋한다.
  - 로봇이 네트워크에서 사라짐: 휴대폰 핫스팟이 너무 멀었다(사용자 확인).
  - 앞오른쪽 바퀴가 안 돎: 사용자가 하드웨어를 고쳤다. 바퀴별 확인용 `wheel_check` 노드를 추가했다.
  - motion_test 전진 64%, 회전 25% FAIL: 펌웨어 가속과 4륜 미끄러짐 때문이며 odom 은 정상(지도가 깨끗함). 이 시험은 실제 로봇에서 명령값 기준이라 맞지 않는다.
  - 첫 지도는 저장 명령이 실행되지 않아 사라져 다시 만들었다. 저장 뒤 `ls` 로 파일을 확인하도록 안내를 바꿨다.
  - 구석 출발에서 못 빠져나옴, 도착 방향 맞추기에서 막힘: 실제 회전이 명령의 약 25% 인데 속도 제한 1.0 rad/s, 진행 감시 15초/30 cm 에 걸렸다. `nav2_params_real.yaml` 만 조정(도착 방향 무시, 진행 감시 30초/15 cm, 회전 상한 1.8, 장애물 여유 0.20 m). 순찰 경로는 방 가운데 4지점으로 바꿨다(`~/maps_real/patrol_route_center.yaml`, 사용자 요청).
  - 손으로 옮긴 뒤 2D Pose Estimate 방향이 틀려 지도와 라이다 벽이 어긋났다: 테이프로 표시한 지도 원점에서 시작하고 키보드로 가운데까지 몰아 해결.

## 2026-11-03 실제 로봇 연결 준비 (VM 미실행, 로봇 미연결)
- 한 일: 실제 로봇을 시뮬레이션과 같은 토픽으로 쓰기 위한 코드와 실행 파일을 만들었다.
  - `robot_bridge`: ESP32 라이다 조각 4개 → `/scan`, 엔코더·자이로 → `/odom`·TF·`/joint_states`. 계산은 `robot_bridge_logic.py`.
  - `tools/microros_udp_relay.py`: 맥에서 로봇 UDP 를 VM agent 로 넘기는 중계(표준 라이브러리만).
  - `tools/install_microros_agent.sh`: VM 에 agent 설치(apt 패키지가 없으면 소스 빌드).
  - `real_bringup` / `real_slam` / `real_nav` launch, `nav2_params_real.yaml`, `route_recorder`(순찰 지점 기록).
  - `detect.launch.py` 에 `use_sim_time`, `route_file` 인자 추가. `alert_notifier` 가 `route_file` 을 받는다.
- 결정과 이유:
  - 사용자가 네트워크 '가'(펌웨어 그대로, 맥이 agent 주소를 맡고 중계)와 범위 A(감지·휴대폰 알림까지)를 골랐다. 목표는 시연 영상(마감 다음 날).
  - 로봇에 올라간 펌웨어 사본(강의 자료의 publish_encoder_gyroz_bat_rssi_lidar_stamped_stable)을 읽어 형식을 맞췄다. 강의 PC 쪽 코드처럼 메시지 시각은 PC 시계를 쓰고, ESP32 시각은 간격 계산에만 쓴다.
  - 바퀴 값은 펌웨어 기준(기어비 298, 반지름 0.0325 m). URDF 의 0.0337 m 는 모양용이라 odom 계산에는 쓰지 않는다.
  - 스캔 시각은 한 바퀴 가운데로 당겼다(0.083초). 다 모인 시각을 쓰면 회전 중 약 6° 어긋난다.
  - AMCL 은 Differential 모델, odom 오차는 기본값 0.2. 시작 위치는 지도 원점(지도를 만들 때 출발한 자리).
  - 실제 공간 지도와 순찰 지점은 공개 저장소에 넣지 않도록 `~/maps_real/` 에 둔다.
- 확인 결과: 맥 단위 시험 103개 통과(pyyaml 환경에서 경로 파일 시험 3개 추가 통과). 가짜 ROS 로 `robot_bridge` 를 돌려 스캔 720점, odom·TF·바퀴 각도·배터리 값 확인. 중계기는 이 컴퓨터 안에서 왕복·재연결·agent 꺼짐을 시험했다.
- 미확인(실제 로봇에서 볼 것): 라이다 방향(앞에 물체를 두고 `scan_check` 의 가장 가까운 각도가 0° 근처인지), 실제 이동 거리와 odom 비율, 핫스팟에서 중계 지연, agent apt 패키지 존재 여부, 감지 기준값.
