## 2026-11-02 텔레그램 알림 구현 (VM 미검증)
- 한 일: `/anomaly/alerts`를 텔레그램으로 보내고 확인 버튼을 `/anomaly/ack`로 전달하는 `alert_notifier`와, 처음 한 번 쓰는 `telegram_setup`을 만들었다.
- 결정과 이유:
  - 사용자가 텔레그램 봇을 골랐다. VM이 먼저 텔레그램 서버에 연결하는 방식이라 VM 네트워크를 바꾸지 않아도 버튼 입력을 받을 수 있다. ntfy는 버튼이 VM으로 직접 들어와야 하고, 웹페이지는 잠긴 휴대폰에 푸시를 띄우기 어렵다.
  - 추가 패키지 없이 표준 라이브러리로 호출한다.
  - 토큰은 저장소 밖 파일에 권한 600으로 저장한다. 토큰이 URL에 들어가므로 오류 메시지에 URL을 넣지 않는다.
  - 전송과 수신은 별도 스레드에서 한다. 인터넷이 끊겨도 감지와 순찰을 막지 않고, 다시 연결되면 순서대로 보낸다.
  - 등록한 대화방의 버튼만 받는다. 사건 번호는 재실행하면 1부터 다시 시작하므로, 이전 실행의 버튼은 실행 번호를 비교해 무시한다.
  - 문구는 측정한 사실만 쓰고 침입자나 사람이라고 단정하지 않는다. 위치에는 좌표와 가장 가까운 순찰 지점 이름을 함께 넣는다.
- 바뀐 파일: `security_patrol/alert_format.py`, `telegram_link.py`, `alert_notifier.py`, `telegram_setup.py`, `launch/detect.launch.py`, `setup.py`, `test/test_telegram_alert.py`, `README.md`
- 확인 결과: 맥 단위 시험 40개 통과(새 시험 16개는 맥의 가짜 HTTP 서버 사용). 재시도, 순서 유지, 토큰 비노출, 다른 대화방 차단, 이전 실행 버튼 차단을 확인했다.
- 미확인: 실제 텔레그램 서버 연결, `telegram_setup` 전체 흐름, 휴대폰 버튼부터 재알림이 멈추기까지. ROS 노드 실행도 VM에서 아직 안 했다.
- 알려진 한계: 대기열은 200개까지이고 넘치면 오래된 알림부터 버린다. `incident_manager`를 다시 켜면 사건 기록이 사라진다.
- 다음 할 일: 사용자가 `@BotFather`로 봇을 만든 뒤 VM에서 `telegram_setup` 실행, 그다음 침입자로 실제 알림과 확인 버튼 시험.
